# Samples

Two real, `dotnet build`-clean solutions generated by AspireForge itself, showing the range between
a bare project and one with production concerns wired in.

## `BasicApi`

```bash
aspireforge new BasicApi
```

Nothing else. The clean-architecture layout, Docker assets, and CI workflow every `aspireforge new`
produces - no database, no auth, no telemetry.

## `ProductionApi`

```bash
aspireforge new ProductionApi
aspireforge add postgres
aspireforge add telemetry
aspireforge add authentication
```

`aspireforge doctor src/ProductionApi.Api` on this one reports **7/10** - authentication, health
checks, HTTPS, CORS, OpenTelemetry, and structured logging all pass. The three that don't are
intentional: global exception handling and a dedicated unit test project have no automatic fix yet
(see [`fix`](../docs/commands/fix.md#fixable-rules-today)), and the architecture check flags the
Api project's direct EF Core reference - a real, known trade-off of today's `add postgres`, not a
bug in the sample.

## Note on `Directory.Packages.props`

This folder has its own (central package management disabled) so the generated projects behave
exactly as they would outside this repository, rather than inheriting AspireForge's own build
configuration.
